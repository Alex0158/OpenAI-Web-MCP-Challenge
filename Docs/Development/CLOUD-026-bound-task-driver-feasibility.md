## Proposed integration contract, not yet accepted or implemented

The next review should settle these concrete boundaries around a demonstrated driver. They are
proposal detail under TASK-035/TASK-029, not a new protocol or accepted production architecture.

1. **Selection:** the user selects one existing task through a trusted local surface. The local
   Adapter verifies runtime connection, owner, and target identity. Host input and a Manifest cannot
   nominate a raw platform task locator; task/device names are display labels, not routing keys.
2. **Enrollment:** record a private pending selection, correlate it with the Receiver's authenticated
   approved Grant and intended account/device/Adapter, and make the binding active only after both
   sides are verified. Interrupted or cancelled approval cannot leave an active delivery binding.
   Duplicate approval must not create a second destination. The exact opaque correlation exchange
   remains to be specified; no public route is implied by this proposal.
3. **Custody and restart:** use a versioned, restrictive local store, owned by the same local user,
   with an atomic durable transition. Keep raw locators private. Restart and credential renewal
   revalidate the same binding; they never search for a replacement or require new Consent merely
   because the Connector was offline. File permissions alone are not owner/account verification.
4. **Delivery:** verify live authority and the exact active binding generation before one bounded
   send. Prefer a real Adapter notification-receive operation represented as structured tool output,
   not an imperative Game command or an impersonated Browser tool result. Allowlist the data fields;
   tool-output role does not make Host data trusted or replace signature and scope checks.
5. **Admission and ambiguity:** persist the intended notification identity and payload digest before
   submitting. A JSON-RPC ID, output label, turn ID, or successful process exit is not idempotency.
   Evaluate structured exact-task item readback for receipt recovery; absent history may mean
   queued or not-yet-persisted input, so absence alone cannot authorize a resend. Unknown outcomes
   remain unknown unless a reviewed runtime contract resolves them.
6. **Scheduling and completion:** distinguish idle turn start from input joining an active turn.
   Coalescing must be bounded and cannot depend on Game effects. After trusted notification handoff,
   no-action, interruption, or incomplete business work does not reopen Receiver delivery. The
   retained effect ACK routes are not repurposed for this new receipt.
7. **Control:** explicit revocation fences future delivery; intentional rebinding is a separate
   trusted user operation and cannot widen the Grant. Lost, wrong-owner, missing, retired, or
   unsupported bindings fail visibly. They do not trigger a new task, credential extraction, or
   an alternate transport.

The smallest counterexamples are: wrong task/account/Grant reaches zero sends; cancelled enrollment
never activates; a crash between approval and local persistence does not misroute; restart retains
the exact target; delayed send after revocation fails; response loss does not blindly resend; and
two distinct allowed signals resolve the same binding. Real runtime and later Game evidence are
additional gates, not replaced by these future unit tests.
