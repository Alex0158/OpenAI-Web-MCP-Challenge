# WebMCP Challenge Governance

**Role:** GOVERNING operational entry point; live Official Rules control  
**Status:** Current routing baseline; refresh volatile facts before submission  
**Primary source:** [Devpost Official Rules](https://webmcp.devpost.com/rules)

## Purpose

This document routes current competition work without duplicating a dated legal snapshot. The live
Official Rules and written organizer clarifications control eligibility, deadline, submission,
judging, rights, and amendment questions. Repository copies, supporter pages, forum posts, and
strategy documents are supporting or historical.

## Current hard-gate categories

Before describing the entry as submission-ready, verify against the live governing sources:

1. entrant and regional eligibility;
2. submission deadline and any amendment;
3. a working judge-accessible Web App;
4. genuine WebMCP implementation and a supported test surface;
5. public source, required assets, instructions, and license;
6. English submission material or required translation;
7. a public functioning demo video within the current duration and audio rules;
8. third-party code, data, media, trademark, and music rights;
9. in-period work and extension rules; and
10. reproducible testing instructions and any credential boundary.

The categories above are routing controls, not a claim that every current detail has been
revalidated on 2026-08-31.

## Evidence and claim boundary

- A local Core test does not prove a live Web App.
- A live URL does not prove judge access, source completeness, or genuine WebMCP invocation.
- A public repository does not prove the submitted deployment matches its source.
- A demo video does not replace runtime or source evidence.
- A candidate scenario or app recommendation is not an app-selection decision.
- A pushed commit is not a Devpost submission readback.

## Refresh protocol

Immediately before app freeze and again before submission:

1. open the live Official Rules, Resources, Updates, and relevant written clarifications;
2. record the current URL, capture time, and changed requirement;
3. reconcile this routing surface, Core/00, Core/06, Core/08, release instructions, repository,
   deployment, video, and submission fields;
4. preserve unresolved ambiguity rather than treating silence as approval; and
5. obtain live Devpost readback before claiming submission.

Do not duplicate volatile dates throughout Core documents. Keep exact current values in one dated
submission or release record when that work begins.
