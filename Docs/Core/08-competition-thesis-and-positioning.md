## 1. Executive thesis

### One sentence

The project extends WebMCP from page-scoped actionability into user-governed re-entry across
time: a later authoritative business event can create bounded pending work, and an available
continuation adapter can return the intended Agent to the canonical page, where fresh state,
current Site Tools, and human controls determine what happens next.

### Short pitch

WebMCP lets a live website expose reliable structured actions to an Agent. Real workflows,
however, often enter a waiting state after the page session or Agent turn ends. When another
person or system changes the business state later, the user normally receives a notification
and must reconstruct the case, prior work, and next action.

This project lets the website define a legitimate future return point and lets the user grant
only narrow continuation authority. A signed business event becomes one accepted pending
delivery, not a free-form prompt and not application truth. When the selected adapter is
available, the bound Agent returns to the authoritative page, rereads current state,
rediscovers the tools valid for that stage, continues the same visible artifact, and stops at
the human decision boundary.

### Current identity boundary

- **Selected:** the domain-neutral re-entry workflow mechanism.
- **Selected Host/demo:** Sleepless Kingdom; shelter-owning player; first-party persistent game;
  `CargoLostToMonster`; bounded `force_recall_soldier`; high-consequence actions remain human-only.
- **Unselected or unproved:** commercial customer and demand, broader Agent doctrine value,
  production continuation transport, hosted true chain, and final market/distribution model.
- **Locally verified reference, product adoption open:** ADR-0043 through ADR-0045/RECORE-007 prove
  the application-neutral v0.2 Host/HTTP/Core/Connector/Adapter chain for repeated ordered signals
  with one active bounded activation. CLOUD-023 separately records the active Receiver's locally
  verified working-tree standing kernel; public controls, pinned release, normal facade, product
  Connector, Game, external runtime, and production evidence remain open.
- **Reference only:** TenderRelay and its tender workflow.
- **Not submission copy yet:** the product promise still requires observed player evidence and a
  clean hosted causal run.

### Selected prototype

Sleepless Kingdom makes the mechanism visible through a world that continues while the player is
away. The player dispatches a gatherer and grants one cargo-loss return. A later server-owned monster
encounter commits `CargoLostToMonster`; the Agent must return to the live shelter page, reread current
mission and causal history, discover the conditional recall tool, and either commit one bounded
recall or show a typed live-state refusal. Migration, siege, destructive upgrades, irreversible
recovery, and actions outside that envelope stay with the human.

The final standing-mode proof then repeats a second eligible signal under the same Consent after the
first effect is acknowledged, while preserving one-active backpressure and revocation. A single
v0.1 cycle remains useful compatibility evidence but does not prove the selected recurring concept.

The current narrow action demonstrates governed temporal re-entry and fresh WebMCP authority. The
stronger claim that natural-language doctrine outperforms transparent deterministic rules remains a
validation hypothesis, not an accepted advantage.

## 2. Problem and value

### Problem class

Web workflows can outlive both a page session and an Agent turn. Later state changes can
invalidate prior assumptions, change permissions, and expose a different set of legitimate
actions. Notifications preserve awareness but not governed Agent continuity; background
automation can preserve activity but may act without the current page, current tools, or a
visible human boundary.

Sleepless Kingdom must still prove a specific real audience, recurring attention/reconstruction
cost, and measurable benefit. Selection makes it the validation target; it does not validate impact.

### Core value

| Value | What the user should experience | Current evidence boundary |
|---|---|---|
| Continuity | The same case, artifact, rationale, and Agent context continue after a real waiting period | Technical continuity is boundedly proven; user value is unproven |
| Control | The user chooses the event, scope, expiry, run limit, and human stop | Receiver-owned bounded consent is proven in the controlled fixture |
| Re-grounding | The Agent returns to application truth instead of acting only from event payloads or stale memory | Canonical page re-entry and fresh state read are proven in controlled runs |
| Stage specificity | The Agent sees only the Site Tools valid for the new workflow state | State-derived tool-surface change is proven in the current local client |
| Shared work | Agent preparation and human review remain visible in the normal web product | Proven in the fixture; selected-app product quality remains open |
| Trust | The user can see why work returned, which authority allowed it, what changed, and what remains human | Correlated bounded evidence exists; production identity and portability remain open |

## 3. Core competitive advantage

The project does not claim to invent notifications, webhooks, queues, Agent triggers,
context resumption, state machines, dynamic tools, or human approval. Its residual advantage
is the governed composition:

> page-authored future re-entry semantics + scoped user grant + typed authoritative event +
> bounded accepted delivery + replaceable continuation adapter + mandatory canonical page
> re-entry + current state-derived Site Tools + visible human boundary

This composition turns a later event into permission to offer bounded continuation, while
keeping authoritative business state in the Host and the governed action surface on the
live page.

| Alternative | What it does well | What the selected mechanism adds |
|---|---|---|
| Notification or deep link | Tells a person that state changed | Preserves governed Agent work and context, then revalidates on return |
| Webhook or workflow engine | Reacts reliably to backend events | Requires page re-grounding, current Site Tools, and a human-visible continuation |
| Generic Agent trigger or resume | Starts or continues an Agent context | Adds website-authored semantics, user scope, typed events, and mandatory current-state checks |
| Browser or DOM automation | Acts through a visual interface | Uses page-native structured tools instead of guessing UI structure or intent |
| Backend API or remote MCP | Exposes structured capabilities outside the page | Keeps the page's live state, session, permissions, dynamic tools, and human UI central |
| Embedded app copilot | Keeps AI inside one product | Lets the user's external Agent collaborate through the app's governed surface |

These are positioning distinctions, not universal superiority claims. A selected workflow
should use the simplest alternative that works. If an authenticated backend job can deliver
the same user outcome without canonical page return or a changed Site Tool surface, this
concept is not material for that workflow.

## 4. Why WebMCP is essential

WebMCP is not an integration badge in this concept. It provides the two page-native anchors:

1. **Enrollment anchor:** the initial page exposes current workflow context and a legitimate
   future re-entry offer under the user's live application session.
2. **Continuation anchor:** the resumed Agent must return to the canonical page, read current
   state, and discover the Site Tools that the application exposes for the new stage.

The human and Agent therefore collaborate against the same visible product state and policy
surface. Removing WebMCP should materially weaken the experience by forcing brittle UI
automation, a separate backend-only control plane, or manual reconstruction. If it does not,
the candidate app fails the WebMCP materiality test.

## 5. Human–Agent operating loop

```text
live WebMCP page
-> Agent reads current context and creates visible revisable work
-> website offers one legitimate future re-entry condition
-> user grants narrow continuation authority
-> page session or Agent turn ends while the business workflow waits
-> authoritative backend emits one typed state-change event
-> Receiver validates and records one bounded pending delivery
-> available adapter activates the intended managed Agent context
-> Agent opens the allowlisted canonical page
-> page verifies fresh state and exposes the new-stage Site Tools
-> Agent continues the same artifact or decision process
-> human reviews and makes the consequential decision
```

The event, accepted delivery, Agent activation, page state, Site Tool invocation, Agent
effect, and human decision are separate facts. The product and demo must not collapse them
into one optimistic status.

## 6. Official challenge alignment

The Official Rules require a WebMCP-powered web app in which people and Agents can interact,
collaborate, and create together. Stage One checks theme fit and reasonable use of WebMCP.
Stage Two weighs WebMCP Leverage, Execution, Potential Impact, and Creativity & Ambition
equally. The official criteria, not this interpretation, control.

| Criterion | Strategic strength | Current weakness | Required proof |
|---|---|---|---|
| Stage One fit | WebMCP is structurally necessary to enrollment and re-entry | The current fixture is not the final web app | A deployed selected-app loop using genuine imperative Site Tool registration |
| WebMCP Leverage | Two-stage discovery, fresh state, changed tools, and page-native action are non-trivial | Current evidence is local and domain-neutral | Genuine initial and resumed Site Tool use in the public judge path |
| Execution | The mechanism has a rigorous bounded implementation and Sleepless Kingdom has substantial local Host/gameplay evidence | The external causal chain and hosted judge journey are incomplete | Manifest/Consent, Event, Connector/Agent return, dynamic recall, effect ACK, deployment, and clean-room run |
| Potential Impact | A persistent game makes off-page attention cost and later-state change concrete | Player demand, frequency, doctrine value, and outcome remain unmeasured | Observed player problem plus a concrete before/after outcome and deterministic-rule comparison |
| Creativity & Ambition | The governed event-to-page re-entry composition is distinctive | Architecture novelty alone is hard to see and easy to overclaim | A domain workflow where the value is visible before the architecture is explained |

### Alignment verdict

**The concept is not off-topic.** It directly explores a future web experience that becomes
more useful when a person and an external Agent share a live application surface across
time. WebMCP is material rather than incidental.

**The current project is not yet a competition-ready product.** Sleepless Kingdom resolves the
application choice, but submitting its current local pieces would still leave a complete external
continuation, clean hosted product experience, and credible observed player problem unresolved.
Selected-app product proof is now the binding competition gate. Additional generic infrastructure
with no Game or Core-contract consumer remains out of scope.

## 7. Claim hierarchy

### Decided

- The re-entry workflow is the selected mechanism.
- Sleepless Kingdom is the selected first Host application and challenge-demo carrier.
- The first bounded Game workflow uses `CargoLostToMonster`, fresh page reads, conditional recall,
  and a human-confirmed high-consequence boundary.
- Website Backend-to-Receiver event semantics are separate from Receiver-to-Agent transport.
- The concrete production transport still requires its own decision and proof.
- TenderRelay is a preserved reference scenario, not the default product.

### Verified, within bounded environments

- Genuine page-bound WebMCP discovery and invocation can occur before and after a workflow
  state change.
- Receiver-owned consent, scoped Grants, typed events, bounded delivery, canonical re-entry,
  fresh state, continued artifact work, and a human stop can compose in one controlled loop.
- Additional local evidence covers replay safety, idempotent effects, selected recovery
  boundaries, and a synthetic crash-recoverable enrollment service contract.

The exact current evidence and its limitations are maintained in
[Core/00](00-current-status.md) and [Core/05](05-validation-and-evidence.md).

### Unselected or unproven

- observed demand, measured player impact, payer/operator model, and final distribution;
- Agent doctrine advantage over deterministic rules and exact-thread advantage over a strong capsule;
- supported production continuation transport and topology;
- cross-user, cross-account, cross-machine, or offline durability;
- public deployment, independent judge reproducibility, and submission status.

No external pitch may promote a target or local bounded result into one of these claims.

## 8. Binding selected-product proof gate

ADR-0042 selects the Host. Sleepless Kingdom must now make all of the following observable:

1. a specific recurring user problem supported by evidence independent of WebMCP;
2. an intrinsic later business event after the initial page session;
3. one persistent artifact, case, or rationale that matters across both stages;
4. a reason the Agent must return to the authoritative page;
5. a visibly changed Site Tool surface after the state transition;
6. meaningful Agent judgment or synthesis that a deterministic Host job cannot replace;
7. a consequential decision that remains human-controlled;
8. a safe, public, synthetic, resettable path that is clear within three minutes; and
9. a material loss of value if WebMCP is removed.

The accepted ADR does not bypass a failed proof gate. A sophisticated story, current implementation
volume, or a high historical score cannot substitute for the named runtime and product evidence.

## 10. Competition proof contract

The final entry must let a judge observe, without first learning the internal architecture:

1. one concrete user problem and initial workflow state;
2. genuine WebMCP context reading and visible Agent-created work;
3. explicit authorization of one future event;
4. the original turn ending and a later authoritative state transition;
5. one accepted pending delivery and separate Agent activation;
6. canonical page re-entry, fresh state, and a changed Site Tool surface;
7. continuation of the same artifact; and
8. a visible human decision plus a correlated safety receipt.

Those per-cycle observations do not alone prove standing authorization. The selected entry must
also show two sequential effect-acknowledged signals under one Consent, one-active backpressure,
restart/replay, and revocation refusing the next signal, as required by TASK-033.

The live app, public repository, short narrated video, testing instructions, and submission
description must all prove the same version and claim boundary. Volatile requirements are
maintained through the [Challenge governance router](../Challenge/README.md)
and must be refreshed against the live Official Rules before release.

## 11. Strategy guardrails

- Optimize for one complete, comprehensible product loop, not the number of tools or modules.
- Show product value before Receiver or transport architecture.
- Do not return to generic platform expansion before proving the selected Game loop.
- Preserve TenderRelay, RightSpot, and other candidates as references or alternatives unless a new
  ADR supersedes the selection.
- Do not let a private adapter, enqueue acknowledgement, scheduled check, or technical trace
  masquerade as supported Agent wake or completed user value.
- Keep ordinary human UI functional; WebMCP should be progressive enhancement for shared
  human–Agent work.
- Stop feature work that does not improve user value, WebMCP materiality, judge
  reproducibility, trust, or a submission hard gate.
